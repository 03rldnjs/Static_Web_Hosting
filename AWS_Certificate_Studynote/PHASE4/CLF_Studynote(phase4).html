리전 선택 고려 사항

도메인 3 클라우드 기술 및 서비스

리전을 고를 때는 아래 네 가지를 비교합니다. AWS 공식 문서에서 제시한 고려 사항입니다.

지연 시간
사용자와 거리가 멀면 지연 시간이 늘어날 수밖에 없으므로 근접성을 고려해야 합니다.
규정 준수
국가(리전)마다 데이터와 서비스 제공에 관한 법적 규제가 다릅니다. 업무가 해당 국가의 법률에 맞는지 확인한 뒤 리전을 골라야 합니다.
서비스 및 기능 가용성
리전마다 지원하는 서비스의 폭이 다를 수 있으므로, 필요한 서비스를 해당 리전이 지원하는지 확인해야 합니다.
비용
같은 서비스라도 리전마다 요금이 다를 수 있으므로 필요한 서비스의 리전별 요금을 비교해야 합니다.

가용 영역(AZ/Availability Zone)

도메인 3 클라우드 기술 및 서비스

  • 리전의 하부 단위입니다. 하나의 리전은 최소 3개의 가용 영역으로 구성됩니다(AWS 자격 시험 기준, AWS 공식 문서).
  • 예외로 미국 서부(캘리포니아)는 신규 계정이 AZ 2개에만 접근할 수 있습니다.
  • 서비스는 여러 AZ에 나누어 배치하는 것을 권장합니다(고가용성 확보).
  • 하나의 AZ에는 최소 1개의 데이터센터가 있습니다.
  • AZ 간에는 매우 빠른 저지연 네트워크로 연결되고, 리전 간에는 AWS 글로벌 네트워크로 연결됩니다.
  • 재해가 나도 고가용성과 내구성을 유지하도록 AZ는 서로 일정 거리 이상 떨어져 있습니다. 다만 같은 리전 안이므로 모든 AZ는 서로 100km 이내에 있습니다. 이로써 여러 재해에 대비하고 안정성을 확보합니다.

AZ 코드와 실제 위치

  • 각 계정별로 AZ의 코드와 실제 위치는 다를 수 있습니다(2025년 11월 이전에 만든 계정, 가장 오래된 리전 기준).
  • 예를 들어 계정 1의 AZ-A와 계정 2의 AZ-A는 같은 이름으로 표시되지만 실제 AZ는 다릅니다(랜덤 배정).
  • 이유는 한 AZ로 트래픽이 몰리는 것을 막고 리소스를 AZ들에 고르게 분산하기 위해서입니다.
  • 계정 간에 AZ를 맞출 때는 AZ ID(예: use1-az1)를 씁니다. AZ ID는 모든 계정에서 같은 물리적 위치를 가리킵니다.
  • 2025년 11월부터 만든 계정은 같은 AZ가 같은 코드로 매핑됩니다.

Edge Location

도메인 3 클라우드 기술 및 서비스

  • Amazon CloudFront(CDN, Content Delivery Network), AWS Global Accelerator 등 여러 서비스를 가장 빠르게 제공(캐싱)하기 위한 거점입니다.
  • 전 세계 여러 장소에 흩어져 있습니다.
  • 사용자가 한 번 불러온 데이터를 엣지 로케이션에 캐싱해 두면, 두 번째 이후 요청은 초저지연으로 콘텐츠를 받을 수 있습니다. 캐싱이므로 컨텐츠를 영구 보관하지는 않습니다.

글로벌 서비스와 리전 서비스

도메인 3 클라우드 기술 및 서비스

글로벌 서비스

  • Amazon CloudFront(CDN)
  • IAM(Identity and Access Management)
  • Amazon Route 53(DNS, Domain Name System)
  • AWS WAF(Web Application Firewall): Layer 7(애플리케이션 레이어) 보안 담당

리전 서비스

  • 대부분의 서비스

AWS WAF는 CloudFront에 사용할 때는 글로벌 범위(미국 동부(버지니아 북부) 리전에서 생성)이고, ALB나 API Gateway 같은 리전 리소스에 사용할 때는 해당 리전 범위입니다.

S3는 글로벌 서비스가 아닙니다

  • S3 버킷 이름은 전 세계에서 유일해야 해서 글로벌 서비스로 오해하기 쉽습니다. 하지만 S3에 저장되는 데이터는 리전에 한정되므로 글로벌 서비스라고 할 수 없습니다.
  • 일반 용도 버킷은 기본적으로 글로벌 네임스페이스(이름이 모든 계정과 리전에서 고유해야 함)에 만들어집니다. 2026년 3월부터는 내 계정만 쓸 수 있는 계정 리전 네임스페이스(이름이 -an으로 끝남)도 선택할 수 있습니다.
  • 계정 리전 네임스페이스를 쓰더라도 데이터는 선택한 리전에 저장됩니다. 기존 글로벌 버킷의 이름은 이 방식으로 바꿀 수 없습니다.

보안과 IAM

Amazon Resource Name(ARN)

도메인 2 보안 및 규정 준수

  • AWS가 제공하는 모든 리소스의 고유 아이디입니다.
  • 형식: arn:partition:service:region:account-id:resource
  • IAM 정책(JSON)의 Resource 항목에서 와일드카드(*)로 다수의 리소스를 지정할 수 있습니다. 예: arn:aws:s3:::버킷이름/*

루트 유저(Root User)

도메인 2 보안 및 규정 준수

  • Root User 계정을 만들면 모든 권한을 자동으로 가집니다.
  • 계정을 만들 때 쓴 이메일 주소로 로그인합니다.
  • 탈취당하면 복구가 매우 어렵습니다. 루트 계정의 사용을 자제하고 MFA(Multi-Factor Authentication)를 설정해야 합니다.
  • 관리용으로만 사용하는 것을 권장합니다(ex. 계정 설정 변경, Billing 등). 일상적인 사용에서는 IAM User나 Role을 만들어 최소한의 권한을 부여하여 이용하는 것이 강력히 권장됩니다.

자주 나오는 오개념

  • 루트 유저도 AWS API를 호출할 수 있습니다(권장하지 않음). “API 호출이 불가능하다”는 설명은 오개념입니다.
  • 보안상 Access Key와 Secret Access Key를 부여하지 않는 것이 좋지만 불가능한 것은 아닙니다. “생성이나 발급이 불가하다”는 설명도 오개념이며, 최대 2개까지 생성할 수 있습니다.

IAM User

도메인 2 보안 및 규정 준수

  • IAM(Identity and Access Management)으로 만든 유저이며, 만들 때 주어진 아이디로 로그인합니다.
  • 기본 권한이 없습니다. 권한을 부여할 수 있는 주체(루트 또는 IAM 권한이 있는 관리자)가 따로 권한을 부여해야 하며, 최소 권한 원칙을 지키는 것이 권장됩니다. 처음 만들 때 권한이나 정책을 주지 않았다면 어떤 권한도 없는 상태(암묵적 거부)입니다.
  • 사람이 아닌 애플리케이션 같은 가상의 주체를 대표할 수도 있습니다.
  • 콘솔에 접근할 때는 비밀번호를, CLI/SDK로 접근할 때는 Access Key와 Secret Access Key를 가집니다.(Access Key와 Secret Access Key는 IAM User 생성 시 자동으로 발급되는 것이 아닙니다. 별도의 발급과정을 거쳐야 발급됩니다.)
  • AWS API를 호출할 수 있습니다. 비유하자면 Access Key는 아이디, Secret Access Key는 패스워드에 해당합니다.
  • AWS 관리를 제외한 모든 작업은 IAM User를 만들어 사용하는 것이 권장됩니다.
  • IAM User에 관리자 권한을 부여하더라도 Root 계정 전용 작업(계정 이름·이메일·루트 비밀번호 변경, 계정 해지, 지원 플랜 변경 등)은 할 수 없습니다. 또한 빌링(Billing) 관련 권한은 Root User가 별도로 허용해야 합니다.

IAM 소개

도메인 2 보안 및 규정 준수

  • AWS 리소스에 대한 인증(Authentication)과 인가(Authorization)를 중앙에서 관리하는 서비스로, 서비스와 리소스에 대한 액세스를 안전하게 관리합니다.
  • IAM User와 Group을 만들고 관리하며 AWS 리소스에 대한 액세스를 허용하거나 거부합니다.
  • AWS 계정 관리와 리소스, 사용자, 서비스의 권한 제어(서비스 사용을 위한 인증 정보 부여), 사용자 생성과 관리, 계정 보안(사용자 패스워드 정책 관리, 일정 시간마다 패스워드 변경 등), 다른 계정과의 리소스 공유 등을 할 수 있습니다.
  • 계정에 별명을 부여하면 로그인 주소를 만들 수 있습니다.
  • IAM은 글로벌 서비스입니다. 리전에 종속되지 않고 전 세계 모든 리전에서 동일하게 적용되어, 리전과 상관없이 사용할 수 있습니다.
  • 최소 권한의 원칙(Least Privilege): 기본적으로 모든 요청은 암묵적으로 거부(Implicit Deny)되어 있습니다. 필요한 권한만 최소한으로 부여하는 것이 AWS 보안의 기본입니다.
  • 무료 서비스입니다. IAM 사용 자체로는 비용이 들지 않습니다.

IAM 개요

도메인 2 보안 및 규정 준수

IAM User
IAM 사용자입니다.
IAM Group
IAM User들의 집합입니다. 그룹에 Policy를 Attach하고 그룹에 User를 추가하면 같은 권한을 여러 User에게 한 번에 줄 수 있어 편리하고 관리가 쉽습니다.
  • 그룹 자체는 로그인하거나 인증받을 수 없고, 그룹 안에 그룹을 넣을 수 없습니다.
  • 한 User가 여러 Group에 포함될 수 있습니다.
IAM Role
사용자, AWS 서비스, 다른 계정 등이 임시로 맡을(assume) 수 있는 권한 묶음입니다(임시 자격 증명 사용). 예: EC2 인스턴스가 키 없이 S3에 접근하도록 Role을 연결합니다.
  • 장기 자격 증명(비밀번호, Access Key)이 없고 임시 보안 자격 증명(STS)을 사용합니다.
IAM Policy(정책)
User, Group, Role이 무엇을 할 수 있는지를 적은 JSON 형식의 문서입니다. 동작 원리는 아래 항목에서 설명합니다.

Root User는 IAM으로 만든 개체가 아니라 계정 자체의 최고 관리자이므로 IAM의 구성 요소에 포함되지 않습니다.

IAM Policy와 동작 원리

도메인 2 보안 및 규정 준수

Policy는 JSON 형식 문서로 작성되며, “누가 무엇을 할 수 있는지”를 정의합니다.

평가 원리

  • 기본 상태: Implicit Deny(암묵적 거부)
  • Allow 정책이 있으면 Allow
  • Allow와 Deny가 동시에 있으면 Deny 우선

핵심

  • 명시적 거부(Explicit Deny)가 항상 명시적 허용을 압도합니다.

예시

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
  • Effect: Allow(허용) 또는 Deny(거부)
  • Action: 수행할 작업
  • Resource: 대상 리소스

IAM Permissions Boundary(권한 경계)

심화 내용(SAA-C03 범위)

Permissions Boundary란?

  • IAM 사용자나 역할에 일반적인 정책을 아무리 많이 붙여도, 권한 경계가 그어 놓은 한계선을 넘는 권한은 행사할 수 없게 막는 경계입니다.
  • Permissions Boundary 자체는 권한을 부여하지 않고, 개체가 가질 수 있는 권한의 상한선만 정합니다.

작동 방식

  • 사용자의 최종 실행 권한은 IAM 정책과 Permissions Boundary의 교집합으로 결정됩니다.
  • 예를 들어 사용자의 IAM Policy에 모든 권한이 붙어 있어도 Permissions Boundary가 S3로 한정되어 있으면, 그 사용자는 S3에만 접근할 수 있습니다.

사용 이유

  • 대표적인 목적은 권한 상승(Privilege Escalation) 방지와 권한 위임입니다.
  • 시나리오: 회사의 중앙 보안팀이 개발자 팀에게 필요한 IAM Role과 User를 스스로 만들 수 있는 권한을 위임하려고 합니다.
  • 위험 요소: 개발자가 마음대로 IAM Role을 만들 수 있으면, AdministratorAccess 권한을 가진 최고 관리자 역할을 새로 만들어 스스로 부여할 위험이 있습니다(권한 상승).
  • 해결책: 개발자에게 IAM User/Role 생성 권한을 주되, 새로 만드는 모든 User/Role에는 반드시 지정된 Permissions Boundary를 붙여야만 생성되도록 조건을 걸어 둡니다.

간단 요약

  • Permissions Boundary는 권한을 직접 주는 게 아니라, IAM User/Role이 넘지 못할 최대 권한의 상한선을 설정하는 기능입니다.
  • 개발자에게 IAM Role 생성 권한을 안전하게 위임(권한 상승 방지)할 때 씁니다.

Permissions Boundary vs SCP vs Resource-based Policy

심화 내용(SAA-C03 범위)

시험에서 자주 헷갈리는 세 가지입니다.

Permissions Boundary
  • 적용 대상: 단일 IAM User/Role
  • 목적: 특정 사용자/역할의 권한 상한선 지정, 권한 상승 방지
  • Root 사용자 영향: 영향 없음
SCP(Service Control Policy)
  • 적용 대상: AWS Organizations의 계정/OU 전체
  • 목적: 계정 전체에 허용되는 권한의 최대 범위를 제한(예: 특정 AWS 서비스 사용 자체를 금지)
  • Root 사용자 영향: 멤버 계정의 Root 사용자를 포함한 계정 내 모든 사용자에게 영향
  • 단, Organizations의 관리 계정(Management Account)에는 적용되지 않습니다.
Resource-based Policy
  • 적용 대상: S3, SQS 등 특정 리소스 자체
  • 목적: 리소스에 접근할 수 있는 외부/내부 주체 지정

Amazon EC2

EC2(Elastic Compute Cloud) 개요

도메인 3 클라우드 기술 및 서비스

AWS 클라우드에서 제공하는 가상 서버 서비스입니다. Elastic이라는 이름처럼 필요한 만큼 클릭 몇 번으로 수 분 만에 서버를 만들고, 사양을 자유롭게 바꾸거나 삭제할 수 있습니다.

핵심 구성 요소 4가지

AMI(Amazon Machine Image)
서버의 템플릿(붕어빵 틀)입니다. OS 종류와 사전 설치된 소프트웨어가 담겨 있습니다.
  • AMI로 EC2를 복제할 수 있고, 다른 리전으로 복사하거나 다른 계정과 공유할 수 있습니다.
  • 스냅샷을 기반으로 AMI를 만들 수 있습니다.
인스턴스 유형
서버의 사양(CPU, 메모리, 그래픽 카드 등)을 결정합니다.
EBS(Elastic Block Store)
EC2 인스턴스에 붙여 쓰는 가상 하드디스크입니다.
보안 그룹(Security Group)
EC2를 보호하는 가상 방화벽입니다.

EC2 인스턴스 구매 옵션

도메인 4 요금 및 지원

On-Demand
장기 약정 없이 사용한 만큼만 초 단위로 지불합니다. 유연하지만 시간당 가격이 가장 비쌉니다. 예측하기 어려운 단기 워크로드나 처음 하는 테스트와 개발 환경에 알맞습니다.
Savings Plans
1년 또는 3년 동안 시간당 일정 금액의 사용을 약정하고 할인을 받습니다(아래 Savings Plans 항목 참고). 리전이나 인스턴스 패밀리를 유연하게 바꾸며 장기 사용할 때 알맞습니다(Compute Savings Plans 기준).
Reserved Instances(RI)
일정한 인스턴스 구성을 1년 또는 3년 약정해 큰 할인(최대 72%)을 받습니다. 특정 AZ를 지정한 RI(Zonal RI)는 그 AZ의 용량도 예약합니다. 예측 가능하고 지속적인 사용에 알맞습니다.
Spot Instance
AWS의 남는 여유 컴퓨팅 용량을 저렴하게(최대 90% 할인) 사용합니다. AWS가 용량이 필요하면 2분 전에 알린 뒤 인스턴스를 회수하므로 중단될 수 있습니다. 중단되어도 괜찮은 워크로드(배치 작업, 빅데이터, 유전체 분석 등)에 알맞습니다.
Dedicated Hosts
고객 전용 물리 서버 전체를 할당받습니다. 소켓/코어 기반의 기존 소프트웨어 라이선스(BYOL)를 지켜야 하거나 엄격한 규정 준수가 필요할 때 알맞습니다.
Dedicated Instances
다른 고객과 물리 하드웨어를 공유하지 않는 인스턴스입니다. 하드웨어 격리가 필요할 때 씁니다.
On-Demand Capacity Reservations
특정 AZ의 EC2 용량을 확보합니다. 필요할 때 인스턴스를 시작할 수 있도록 용량을 미리 잡아 둡니다.
Capacity Blocks for ML
GPU 가속 인스턴스를 특정 기간에 예약합니다. ML 학습처럼 GPU 용량이 정해진 시간대에 필요할 때 씁니다.

Savings Plans

도메인 4 요금 및 지원

1년 또는 3년 동안 시간당 일정 금액의 컴퓨팅 사용량을 약정하고, 약정에 해당하는 사용량에 할인 요금을 적용받는 방식입니다.

  • 예를 들어 시간당 1달러를 약정하면 매 시간 1달러어치 사용량을 약정하는 것이며, 인스턴스 한 대를 예약한다는 뜻이 아닙니다.
  • 약정 범위에 해당하는 사용량에는 Savings Plans 할인 요금이 적용됩니다.
  • 약정 범위를 넘는 사용량에는 일반적으로 On-Demand 요금이 적용됩니다.
  • 약정한 사용량을 채우지 못한 시간에도 쓰지 않은 약정분에 비용이 발생할 수 있습니다.

실제 사용량이 장기간 안정적이면 유리합니다. 하지만 앞으로의 사용량을 예측하지 못한 채 지나치게 큰 약정을 하면 절감 효과가 작아지고, 쓰지 않는 약정분 비용까지 낼 수 있습니다.

두 가지 주요 유형

Compute Savings Plans(높은 유연성)
EC2 인스턴스 패밀리, 크기, 리전, 운영체제 등이 달라져도 폭넓게 적용됩니다. EC2뿐 아니라 AWS Fargate와 AWS Lambda의 적격 사용량에도 적용됩니다.
  • 예: c7i에서 m7i로 변경
  • 예: 서울 리전에서 다른 리전으로 워크로드 이전
  • 예: EC2에서 Fargate로 워크로드 이전
위 변화가 있어도 적격 사용량에 대한 할인 혜택이 유지됩니다.
EC2 Instance Savings Plans
선택한 리전과 인스턴스 패밀리에 약정하는 대신 더 높은 할인율을 받는 유형입니다. 인스턴스 크기, 운영체제, 테넌시를 바꿔도 약정 조건을 충족하면 할인 혜택이 유지됩니다.
  • 예: 서울 리전의 m7i 패밀리에 약정
  • 예: m7i.large에서 m7i.2xlarge로 크기 변경
  • 예: 같은 패밀리 안에서 운영체제 변경
단, 다른 인스턴스 패밀리로 바꾸거나 다른 리전으로 이동하면 해당 사용량은 이 약정의 적용 범위를 벗어날 수 있습니다.

Savings Plans와 RI의 관계

둘 다 장기 약정으로 할인을 받지만 약정 방식이 다릅니다. Savings Plans는 시간당 금액 기준으로 사용량을 약정하고, RI는 특정 인스턴스 구성 또는 패밀리, 리전 등의 조건에 따라 할인을 받습니다. RI는 유형에 따라 조건과 유연성이 달라집니다.

EC2 스토리지: EBS와 인스턴스 스토어

도메인 3 클라우드 기술 및 서비스

EBS(Elastic Block Store)

  • 네트워크로 연결된 가상 디스크입니다.
  • 인스턴스를 중지(stop)했다가 다시 시작해도 데이터가 영구 보존됩니다. 삭제(terminate)할 때는 루트 볼륨이 기본적으로 함께 삭제됩니다(아래 “Terminate 시 EBS 삭제 여부” 참고).
  • 독립적으로 스냅샷을 찍어 백업할 수 있습니다(스냅샷은 S3에 저장).
  • 기본적으로 한 번에 하나의 EC2에 연결합니다. io1·io2 볼륨은 Multi-Attach로 같은 AZ의 여러 인스턴스에 연결할 수 있습니다.
  • EC2와 같은 AZ에 존재합니다.

인스턴스 스토어

  • EC2의 물리 서버에 직접 붙어 있는 고성능 스토리지입니다(주로 서버 메인보드에 꽂힌 SSD).
  • 서버 바로 옆에 있어 네트워크를 거치지 않고 I/O를 하므로 속도가 극도로 빠릅니다(최고의 I/O 성능).
  • 휘발성입니다. EC2 인스턴스를 중지하거나 삭제하면 데이터가 모두 사라집니다.

Snapshot

도메인 3 클라우드 기술 및 서비스

  • 특정 시점의 EBS 상태를 저장한 것입니다. 필요하면 스냅샷으로 그 시점의 EBS를 복구할 수 있습니다.
  • S3에 증분식으로 보관됩니다. 증분식 저장은 첫 백업 이후 변경되거나 추가된 데이터 블록만 골라서 저장하는 방식입니다.

Terminate 시 EBS 삭제 여부

심화 내용(SAA-C03 범위)

루트 볼륨
기본값은 DeleteOnTermination = True입니다. 기본 설정에서는 인스턴스를 삭제하면 루트 볼륨도 함께 삭제됩니다. 인스턴스를 만들 때나 설정에서 이 플래그를 False로 바꾸면 인스턴스를 삭제해도 루트 EBS 볼륨이 삭제되지 않고 남습니다.
추가로 연결한 데이터 볼륨(Non-Root EBS)
기본값은 DeleteOnTermination = False입니다. 루트 볼륨 외에 추가로 붙인 EBS 볼륨은 인스턴스를 삭제해도 자동으로 삭제되지 않고 분리된 채 계정에 남습니다.

자주 나오는 유형(SAA-C03 기준)

  • 상황: 실수로 EC2 인스턴스를 삭제하더라도 루트 EBS 볼륨의 중요한 데이터가 함께 삭제되지 않게 하려는 경우
  • 정답: 루트 볼륨의 DeleteOnTermination 속성을 False로 설정

EC2 인스턴스 수명 주기

도메인 3 클라우드 기술 및 서비스

Pending
인스턴스 시작을 준비하는 단계입니다. 이후 Running 상태로 바뀝니다.
Running
인스턴스가 실행 중인 단계입니다. EC2 컴퓨팅 사용 요금이 발생합니다.
Stopping
인스턴스를 중지하는 중입니다. 최대 절전 모드(Hibernation)를 사용 중이면 이 상태에서도 인스턴스 요금이 발생합니다.
Stopped
인스턴스 중지가 끝난 단계입니다. 다시 시작할 수 있고, EC2 요금은 부과되지 않지만 EBS 요금은 부과됩니다.
Shutting-down
인스턴스를 종료하는 중입니다. 인스턴스 사용 요금 청구가 중단됩니다.
Terminated
인스턴스가 영구적으로 종료된 상태입니다. 다시 시작할 수 없고, 기본 설정이면 붙어 있던 루트 EBS 볼륨도 함께 삭제됩니다.

Stop, Reboot, Terminate, Hibernate

도메인 3 클라우드 기술 및 서비스

Stop / Start(중지 후 다시 시작)
컴퓨터를 껐다 다시 켜는 것과 비슷합니다. 일반적으로 EBS 데이터는 유지되지만 RAM 내용과 Instance Store 데이터는 유지되지 않습니다. 다시 시작할 때 Elastic IP를 할당하지 않았다면 Public IP 주소가 바뀔 수 있습니다.
Reboot(재부팅)
운영체제를 다시 부팅하는 동작입니다. 잠시 재부팅 상태를 거쳐 다시 running 상태로 돌아옵니다. 중지 후 시작과는 다르며, 보통 같은 호스트에서 재부팅해서 Private IP와 Public IP, Instance Store 데이터가 그대로 유지됩니다. 인스턴스 사용 요금도 계속 발생합니다.
Terminate(종료)
인스턴스 자체를 폐기하는 동작입니다. 다시 시작할 수 없습니다. EBS 루트 볼륨은 기본적으로 삭제되지만 설정에 따라 유지되게 할 수도 있습니다.
Hibernate(최대 절전 모드)
일반 Stop과 달리 RAM 내용을 EBS 루트 볼륨에 저장한 뒤 중지하고, 다시 시작할 때 복원합니다. 일반 Stop은 RAM 내용이 사라집니다. 두 경우 모두 stopped 상태에서는 EC2 인스턴스 사용 요금이 발생하지 않지만 EBS 저장 요금은 발생합니다.

EC2 배치 그룹(Placement Groups)

심화 내용(SAA-C03 범위)

Cluster
  • 배치 방식: 단일 AZ 안에서 인스턴스들을 물리적으로 서로 가장 가까운 곳에 빽빽하게 모아 배치합니다.
  • 장점: 네트워크 지연 시간이 극도로 낮고 네트워크 처리량이 극도로 높습니다.
  • 단점: 같은 하드웨어에 장애가 나면 그룹 안의 모든 인스턴스가 한꺼번에 영향을 받습니다(장애 위험이 큼).
  • 주요 용도: HPC(High Performance Computing), 빅데이터 수집, 인스턴스 간 초고속 통신이 필수인 워크로드
Spread
  • 배치 방식: 인스턴스들을 서로 다른 물리적 하드웨어에 하나씩 따로 떨어뜨려 배치합니다.
  • 장점: 하드웨어 장애가 나도 다른 인스턴스에 영향을 주지 않아 장애 격리(Fault Tolerance)와 고가용성이 극대화됩니다.
  • 제약: AZ당 최대 7개 인스턴스까지만 배치할 수 있습니다.
  • 주요 용도: 물리 하드웨어 문제로 같이 죽으면 안 되는 소수의 핵심 인스턴스(메인 DB, 도메인 컨트롤러 등)
Partition(파티션 배치 그룹)
  • 배치 방식: 배치 그룹을 여러 파티션으로 나누고, 각 파티션은 서로 다른 랙(Rack)을 사용합니다. 인스턴스는 파티션 안에 여러 개 들어갈 수 있습니다.
  • 특징: 파티션 A의 랙이 고장 나도 파티션 B, C의 인스턴스는 안전합니다.
  • 주요 용도: Hadoop, Cassandra, Kafka 같은 대규모 분산 데이터 처리 시스템

ENI, ENA, EFA 비교

심화 내용(SAA-C03 범위)

ENI(Elastic Network Interface): 기본 가상 랜카드, 모든 인스턴스에서 사용 가능
  • VPC 안에서 EC2 인스턴스에 연결되는 기본 가상 네트워크 인터페이스입니다.
  • 구성 요소: 주 Private IP, 보조 Private IP, Public IP(또는 Elastic IP), MAC 주소, 보안 그룹 등
  • EC2 인스턴스 간에 Attach/Detach 할 수 있습니다.
  • 듀얼 홈드 서버 구성: 하나의 EC2에 ENI 2개를 붙여 용도별로 네트워크 트래픽을 물리적·논리적으로 분리할 수 있습니다.
ENA(Elastic Network Adapter): 고성능 일반 네트워크, 일부 인스턴스에서만 사용 가능
  • 높은 네트워크 대역폭, 높은 초당 패킷 처리량, 낮은 지연 시간을 제공하는 향상된 네트워크 어댑터입니다.
  • 인스턴스 유형에 따라 최대 200Gbps까지 대폭 향상된 대역폭을 제공합니다.
  • 운영체제 커널 수준에서 네트워크 처리를 최적화하며, 일반적인 웹 애플리케이션, 대규모 데이터베이스, 네트워크 I/O가 높은 일반 워크로드에서 씁니다.
EFA(Elastic Fabric Adapter): 초저지연 HPC 전용 네트워크, 일부 인스턴스에서만 사용 가능
  • HPC(고성능 연산)와 머신러닝(ML) 학습을 위해 만든 특수 목적용 어댑터입니다.
  • OS 커널 우회: 데이터를 보낼 때 운영체제 커널을 거치지 않고 애플리케이션이 네트워킹 하드웨어와 직접 통신해 지연 시간이 극도로 낮습니다.
  • OS-bypass 특성 때문에 Linux 인스턴스에서만 지원됩니다.
  • OS-bypass 트래픽은 라우팅되지 않아 같은 서브넷 안의 인스턴스 간 연결에서만 동작합니다(인터넷이나 VPC 간 트래픽은 지원하지 않음).

Jumbo Frame

심화 내용(SAA-C03 범위)

  • 네트워크에서 한 번에 실어 나를 수 있는 패킷의 최대 크기를 크게 늘려 네트워크 처리 효율을 높이는 기술입니다.
  • MTU(Maximum Transmission Unit)는 네트워크로 전송할 수 있는 단일 프레임/패킷의 최대 크기입니다. 표준 Ethernet MTU는 1500Bytes, Jumbo Frames MTU는 9001Bytes(AWS 기준)입니다.

왜 사용할까?

15000byte 데이터를 보낸다고 가정합니다.

  • 표준 프레임: 데이터를 10개로 쪼개 보내야 합니다. 패킷마다 네트워크 헤더(주소, 제어 정보 등)가 붙고 CPU가 패킷을 10번 처리해야 해서 프로세서 부하(Overhead)가 생깁니다.
  • Jumbo Frame: 데이터를 2개의 큰 덩어리로 나눠 보냅니다. 헤더 오버헤드와 CPU 연산 부담이 크게 줄어 전송 성능이 좋아집니다.

AWS EC2에서 Jumbo Frame을 쓸 수 있는 조건

지원되는 경우

  • 같은 VPC 안의 EC2 인스턴스 간 통신
  • 같은 리전의 VPC 피어링으로 연결된 VPC 간 통신
  • AWS Direct Connect를 통한 온프레미스와 AWS 전용선 통신

표준 프레임 등으로 제한되는 경우

  • 인터넷 게이트웨이를 거쳐 외부로 나가는 트래픽(1500)
  • VPN 연결(Site-to-Site VPN 등)(1500)
  • AWS 리전 간 트래픽(1500, Transit Gateway를 쓰면 별도 규정)
  • 리전 간 VPC 피어링 트래픽(8500)

Public, Private, Elastic IP 주소

도메인 3 클라우드 기술 및 서비스

Public IP
  • 인스턴스를 stop하면 반환(release)되어, 다시 시작할 때 다른 IP 주소로 바뀝니다.
  • Public Subnet에서 사용합니다.
  • 비용이 발생합니다.
  • 인스턴스의 Private IP와 연동됩니다.
  • 인스턴스 간에 옮길 수 없습니다.
Private IP
  • 인스턴스가 stop 상태여도 IP 주소가 유지됩니다.
  • Public Subnet과 Private Subnet 모두에서 사용합니다.
Elastic IP
  • 고정된(정적) Public IP입니다.
  • 비용이 발생합니다.
  • 인스턴스의 Private IP와 연동됩니다.
  • 인스턴스나 ENI 간에 옮길 수 있습니다.

Public Subnet과 Private Subnet

도메인 3 클라우드 기술 및 서비스

Public Subnet
라우팅 테이블에 0.0.0.0/0 → IGW(인터넷 게이트웨이) 설정이 있습니다. 인스턴스에 Public IP가 있고 보안 설정이 허용하면 외부 인터넷에서 직접 접근할 수 있습니다.
Private Subnet
인터넷 게이트웨이로 통하는 직통 경로가 없습니다. Public IP가 부여되지 않거나 외부에서 직접 인바운드 접근을 할 수 없습니다.

Bastion Host와 SSM Session Manager

심화 내용(SAA-C03 범위)

개념과 필요성

프라이빗 서브넷의 서버에는 외부 인터넷에서 직접 SSH/RDP로 접속할 수 없습니다. 그렇다고 관리를 위해 DB 서버에 Public IP를 붙이면 보안에 치명적입니다. 이때 외부 관리자가 프라이빗 서브넷 안의 서버에 안전하게 접속하도록 중간 길목 역할을 하는 전용 EC2 인스턴스가 Bastion Host입니다.

인터넷에서 Private Subnet 전체로의 접근을 허용하는 것이 아니라, Bastion Host를 거쳐 허용된 Private 서버에만 관리자가 접근하는 구조입니다.

구축과 보안 설정 모범 사례

  • 위치: 반드시 Public Subnet에 두며 Public IP를 가집니다.
  • Bastion Host의 보안 그룹: Inbound SSH(22) 또는 RDP(3389)를 관리자의 특정 IP 대역만 허용합니다(0.0.0.0/0 전체 허용 금지).
  • Private EC2의 보안 그룹: Inbound SSH(22)를 오직 Bastion Host의 Security Group ID만 허용합니다.

현대적 대안: AWS Systems Manager(SSM) Session Manager

최근 시험과 실무에서는 Bastion Host 대신 SSM Session Manager를 쓰는 구조가 점점 널리 쓰입니다.

Bastion Host의 단점

  • Bastion Host 인스턴스를 직접 유지 관리해야 합니다.
  • Port 22(SSH)를 열어 둬야 해서 관리 부담과 보안 위험이 있습니다.

SSM Session Manager의 장점

  • Bastion Host가 필요 없습니다.
  • Port 22를 열 필요가 없어 보안 그룹 인바운드 규칙을 0개로 둘 수 있습니다.
  • Public IP 없이도 AWS IAM 권한과 SSM Agent로 웹 콘솔/CLI에서 Private 인스턴스에 바로 터미널로 접속할 수 있습니다.

VPC 네트워킹: NAT와 VPC Endpoint

NAT Gateway: 개념과 필요성

도메인 3 클라우드 기술 및 서비스

Network Address Translation이 정확히 무슨 뜻인가?

  • Private IP를 사용하는 인스턴스의 트래픽을 NAT Gateway가 Elastic IP(= 고정 Public IP)를 사용해 인터넷으로 나갈 수 있도록 주소를 변환함
  • 그래서 인터넷에서는 NAT Gateway의 Public IP에서 온 요청처럼 보임
  • 인터넷에서 응답이 돌아오면 NAT Gateway가 다시 Private IP로 변환하여 EC2로 전달함
  • 이 과정이 바로 Network Address Translation

NAT Gateway가 왜 필요한가?

  • Private Subnet의 EC2가 인터넷에서 직접 접근받을 수 없게 만들면서도, EC2가 인터넷 환경에 나가서 패키지를 다운로드하거나 외부 API를 호출하는 것은 허용하고 싶은 상황
  • NAT가 Private Subnet → Internet 방향의 outbound 통신을 가능하게 해줌
  • 또한 Internet → Private EC2의 연결을 인터넷에서 선제적으로 진행하는 것은 허용하지 않음

NAT Gateway와 NAT instance의 중요 포인트

  • NAT Gateway와 instance가 인터넷으로 바로 연결해주는 것이 아니라, NAT Gateway → Internet Gateway → Internet의 구조 (결국 Internet으로 연결하는 직접적인 요소는 Internet Gateway이고, NAT Gateway는 Private IP를 사용하는 리소스가 Internet으로 나갈 수 있도록 NAT를 수행하는 장치)
  • NAT Gateway와 NAT instance 모두 기본적으로 Public Subnet에 배치(단순히 이름이 Public인 것이 아니라, Route Table에 Internet Gateway로 향하는 경로가 존재하는 Subnet)

NAT Gateway 고가용성과 Regional NAT Gateway

심화 내용(SAA-C03 범위)

고가용성 확보와 AZ 장애에 대비한 NAT Gateway 아키텍처

  • 하나의 NAT Gateway를 여러 AZ에서 공유하다가 NAT Gateway가 있는 AZ에 장애가 발생하면 다른 AZ의 리소스들도 인터넷 액세스를 잃을 수 있음
  • 따라서 고가용성과 장애 대비를 원한다면 각각의 AZ에 하나씩 NAT Gateway를 배치하여 하나의 AZ에 장애가 발생했을 때 다른 AZ의 인터넷 액세스에 영향이 없도록 하는 것이 고가용성을 확보하는 아키텍처임(단, 비용적인 측면에서는 더 비쌀 수밖에 없음. 따라서 위의 상황이 아니고, 비용을 최소한으로 사용하기를 원하는 경우에는 하나의 AZ에 NAT Gateway를 배치한 후 공유하는 것이 정답에 가까울 수도 있음)
  • 참고: 2025년 11월 20일부터 NAT Gateway에 리전 가용성 모드(Regional NAT Gateway)가 추가됨
    • 하나의 NAT Gateway가 워크로드가 있는 여러 AZ로 자동 확장되어, AZ마다 NAT Gateway를 따로 만들 필요가 줄어듦(기존의 AZ 단위 방식은 Zonal NAT Gateway라고 부름)
    • Regional NAT Gateway는 VPC 수준의 리소스라서 별도의 Public Subnet이 필요하지 않음
    • 단, Private NAT Gateway는 Regional NAT Gateway에서 지원되지 않고 Zonal 모드로만 가능함

NAT instance의 작동 방식

  • Public Subnet에 EC2를 하나 배치
  • Private EC2의 Route Table: 0.0.0.0/0 → NAT instance
  • NAT instance의 Route Table: 0.0.0.0/0 → Internet Gateway
  • NAT Instance 자체는 인터넷에 접근할 수 있어야하므로 Public Subnet에 있어야하고 Public IP 또는 Elastic IP가 필요

왜 NAT instance를 사용하는가?

  • EC2의 특성상 여러 관리 책임을 사용자가 가지게 됨.
  • 이는 운영 부담을 늘리지만, 그만큼 사용자가 제어할 수 있는 영역도 많아지게 됨.
  • 따라서 특정 네트워크 트래픽을 세밀하게 제어하길 원하거나 사용자 지정 구성, Bastion Host 역할 동시 수행 등을 원하는 경우 NAT instance를 사용하는 것이 더 유리할 수 있음(단, EC2에 NAT와 Bastion Host를 같이 사용하는 것이 일반적인 구조인 것은 아님)

NAT instance와 Bastion Host의 차이점

  • 두 서비스 모두 EC2 인스턴스를 활용하며, 사용자가 대부분의 관리 책임을 가진다는 공통점이 있음
  • NAT instance는 Private Subnet에 있는 EC2로부터 인터넷으로 향하는 Outbound 통신을 가능하게 하는 역할이고, Bastion Host는 외부의 관리자가 Private EC2에 관리 목적으로 접근(Inbound)할 수 있는 진입점 역할을 함.

NAT Gateway vs VPC Endpoint

심화 내용(SAA-C03 범위)

  • 한 줄로 요약하자면, 프라이빗 서브넷을 인터넷에 연결하려면 NAT Gateway, 다른 AWS 서비스 및 PrivateLink 기반 서비스에 연결하려면 VPC Endpoint(without internet)
  • NAT Gateway: Private Subnet → 인터넷
  • VPC Endpoint: Private Subnet → AWS 서비스
  • 상황: Private Subnet에 있는 EC2가 인터넷에 있는 GitHub에서 파일을 다운로드해야한다 → NAT Gateway
  • 상황: Private Subnet에 있는 EC2가 S3에 파일을 업로드해야 한다 → VPC Endpoint

왜 VPC Endpoint를 사용하는가?

  • 가장 중요한 이유는 인터넷을 거칠 필요가 없기 때문
  • 만약 Private EC2가 S3에 접근한다고 할 때, NAT Gateway를 사용하면 NAT Gateway 비용과 데이터 처리 비용 등이 발생할 수 있음(단, 항상 VPC Endpoint가 더 저렴한 것은 아님, 상황에 따라 비용은 역전될 수 있음)
  • 반면에 VPC Endpoint를 활용하면 AWS 서비스로 VPC 내부에서 직접 연결할 수 있음

VPC Endpoint와 NAT Gateway는 역할이 다른만큼 양립가능한 두 서비스임. 즉, 인터넷 접근과 동시에 S3 등의 AWS 서비스에 접근해야하는 경우 두 방식을 모두 사용할 수 있음.

VPC Endpoint의 종류

  1. Gateway Endpoint
    • S3, DynamoDB로의 접근을 원한다면 Gateway Endpoint
    • Route Table에 S3/DynamoDB로의 경로를 추가
  2. Interface Endpoint
    • AWS PrivateLink를 기반으로 함. 대부분의 AWS 서비스/PrivateLink 지원 서비스로의 접근을 원한다면 Interface Endpoint
    • ENI를 생성함(시험에서 Endpoint가 ENI를 생성한다는 표현이 나오면 Interface Endpoint 떠올리기)

Private NAT Gateway

심화 내용(SAA-C03 범위)

  • NAT Gateway는 default로 Public Subnet에 위치하지만, Private Subnet에 배치되는 경우도 있음

Private NAT Gateway가 가지는 차이점

  1. Private Subnet에 배치
  2. 인터넷으로 직접 나가는 데 사용하지 않음
  3. 다른 VPC나 온프레미스 네트워크 등으로 나가는 트래픽의 IP를 변환하는 데 사용
  4. 주로 Transit Gateway 또는 Virtual Private Gateway를 통한 연결과 함께 사용
  • 즉, 인터넷 연결용이 아닌, 사설 네트워크 간 통신에서 주소를 변환하는 용도
  • Private NAT Gateway가 왜 필요한가?
    • 서로 다른 VPC나 사내 네트워크 간 통신에 주로 사용됨. 특히 네트워크 IP 주소가 겹치거나, 상대방에게 내부 EC2의 실제 IP를 노출하고 싶지 않을 경우 유용함.
  • 주소 변환 및 연결 방법
    • VPC → Private NAT Gateway(출발지 IP를 NAT Gateway의 사설 IP로 변환) → Transit Gateway or VPN 연결 → 사내 네트워크 연결

ELB와 Auto Scaling

Scale Up과 Scale Out

도메인 3 클라우드 기술 및 서비스

Scale Up: 수직적 향상 / 성능 향상

  • 인스턴스의 유형/성능 변경, CPU/메모리 증가
  • 일반적으로 인스턴스 유형 변경 시 중지/변경/재시작이 필요할 수 있음
  • 단일 서버의 성능 한계가 존재

Scale Out: 수평적 향상 / 개수 늘리기

  • 실행 중인 인스턴스의 수 늘리기
  • ELB를 통해 트래픽 분산 가능
  • Auto Scaling으로 인스턴스 수 자동 조절 가능
  • 인스턴스들을 여러 AZ에 분산시켜 가용성 향상 가능

Stateless와 Stateful

심화 내용(SAA-C03 범위)

Stateless vs Stateful

  • Stateless = 무상태: 각 요청을 처리할 때 서버 자체에 저장된 이전 요청의 상태에 의존하지 않음
    • 요청마다 필요한 정보를 함께 전달하거나 외부 저장소에서 조회
    • 어떤 서버가 요청을 처리하더라도 동일한 처리가 가능하도록 설계
    • 서버 추가/제거가 상대적으로 쉬움
  • Stateful = 상태 유지: 서버가 이전 요청에서 생성된 상태 정보를 보관하고, 이후 요청에서 이를 활용
    • 서버 메모리에 로그인 세션이나 진행 상태가 저장됨
    • 다음 요청이 다른 서버로 전달되면 상태 정보가 없을 수 있음
    • 상태 공유/동기화 또는 세션 고정 같은 추가 설계가 필요할 수 있음

Stateless + Scale Out

  • Stateful 중심 설계: 특정 서버에 상태가 종속됨 → 만약 요청이 A 서버에 의존하고 있다면, 해당 요청을 B가 처리하기 위해 세션 공유, 세션 고정 등의 추가 조치가 필요함. 또한 A 서버가 종료되면 메모리에만 있던 상태가 사라질 가능성 존재
  • Stateless 중심 설계: 상태가 서버 외부에서 관리됨
    • Auto Scaling으로 EC2를 추가하거나 제거해도 상태 정보가 특정 인스턴스 메모리에만 묶여있지 않으므로 확장과 교체가 쉬워짐(필요한 정보가 특정 서버에 종속되어있지 않으므로 관리에 용이)
    • 장점들
      1. 수평 확장 용이: 새 인스턴스를 추가해도 특정 서버의 세션을 복사할 필요가 줄어듦
      2. 장애 복구 용이: 서버가 종료되더라도 외부에 저장된 상태 정보는 유지됨
      3. 로드 밸런싱 용이: ELB가 요청을 여러 서버에 분산하기 쉬움
      4. 자동화에 적합: Auto Scaling이 인스턴스를 추가하거나 제거하기 편리함

Health Checks와 Grace Period

심화 내용(SAA-C03 범위)

Health Checks: 어떤 상태를 확인하는가?

  • EC2 Status Checks: EC2 인스턴스와 이를 실행하는 기반 시스템에 문제가 있는가?
    1. System Status Check
      • AWS가 관리하는 기반 인프라에 문제가 있는지 확인 ex. 물리적 호스트, 네트워크 또는 전원과 같은 AWS 측 기반 시스템 문제가 원인이 될 수 있음
    2. Instance Status Check
      • EC2 인스턴스 자체의 운영 상태 확인 ex. 운영체제 부팅 문제, 네트워크 설정 문제 또는 메모리/파일 시스템 관련 문제 등이 원인이 될 수 있음
  • ELB Health Checks: 로드밸런서가 등록된 대상에 요청을 보내도 되는지 판단하기 위한 검사
    • ELB가 인스턴스를 비정상으로 판단했다고 해서 Auto Scaling이 반드시 그 인스턴스를 교체하는 것은 아님
      • ELB는 비정상 대상을 일반적인 트래픽 분산에서 제외할 수 있음
      • ASG는 기본적으로 ELB 상태 검사 결과를 무시함
      • ASG에서 ELB Health Checks를 활성화했다면, ELB가 비정상적으로 판단한 인스턴스를 ASG도 비정상으로 판정하고 교체할 수 있음
      • 즉, ELB의 트래픽 분산과 ASG의 인스턴스 교체 판단은 구분해야 함

Health Check Grace Period(유예 기간)

  • 새 인스턴스가 InService 상태에 들어간 뒤, 상태 검사 실패만으로 너무 일찍 교체되지 않도록 ASG가 기다리는 최소 시간
  • ex. Grace Period - 120 sec
    1. EC2 시작 - 인스턴스가 실행되고 애플리케이션이 초기화되기 시작함
    2. 초기화 중 - 아직 애플리케이션이 준비되지 않았다면 /health 요청에 정상 응답하지 못할 수 있음. 따라서 ELB는 대상이 비정상이라고 판단할 수 있음
    3. Grace Period 중 조기 교체 방지 - ASG는 유예 기간을 적용해 새 인스턴스를 성급하게 Unhealthy로 표시하고 교체하지 않도록 함
    4. 120초 경과 - 여전히 상태 검사에 실패하면 ASG가 인스턴스를 비정상이라고 판단하고 교체할 수 있음
    • 유예기간이 EC2의 실제 실행 중단까지 무시하는 것은 아님. 유예 기간 중 더 이상 EC2가 running 상태가 아니라는 것이 감지되면 ASG는 즉시 해당 인스턴스를 비정상으로 표시하고 교체할 수 있음
    • Grace Period는 길수록 좋은가? → X
      • 너무 짧으면: 애플리케이션 초기화가 끝나기 전에 인스턴스가 반복적으로 교체될 수 있음
      • 너무 길면: 실제로 고장 난 인스턴스의 교체가 늦어질 수 있음
      • 따라서 인스턴스 부팅, 애플리케이션 초기화 및 ELB 헬스 체크 통과에 필요한 시간을 고려해 시간을 설정해야 함(AWS 문서 기준 콘솔 생성 시 Default 300sec / CLI or SDK 생성 시 Default 0sec)
  • Grace Period vs Instance Warmup
    • Instance Warmup: 새 인스턴스가 충분히 준비되기 전의 지표가 확장 정책의 판단을 왜곡하지 않도록 함
    • Grace Period: 새 인스턴스가 초기화 중일 때 너무 빨리 비정상 판정을 받고 교체되는 것을 방지

Auto Scaling 유형과 Scaling Policy

심화 내용(SAA-C03 범위)

Auto Scaling Types

  1. Dynamic Scaling(동적 확장)
    • 현재의 트래픽이나 CloudWatch 지표에 따라 용량 조절
    • 현재 부하에 반응해야 하는 상황에 적합
      • 3가지 유형
        1. Target Tracking: 지표를 목표값에 가깝게 유지하도록 자동 조절(ex. CPU 평균 50% 유지, 대상당 요청 수 유지)
        2. Step Scaling: 경보 위반 정도에 따라 조정 규모를 다르게 설정(ex. CPU가 목표를 얼마나 초과했는지에 따라 서로 다른 규모로 확장)
        3. Simple Scaling: 단일 조정 기준으로 용량 변경, 조정 후 쿨다운 적용(ex. 단순한 한 단계 조정과 Cool Down)
  2. Scheduled Scaling(예약 확장)
    • 미리 지정한 날짜와 시간에 용량을 조절
  3. Predictive Scaling(예측 확장)
    • 과거의 사용 패턴을 분석해 미래 수요를 예측하고, 수요가 늘기 전에 용량 준비
  4. Manual Scaling(수동 조절)
    • 관리자가 ASG의 Desired Capacity를 직접 변경
    • 자동 확장 정책이 아닌 관리자의 직접적인 용량 변경이 필요한 상황에 사용

Scaling Policy

  • Dynamic Scaling
    1. Target Tracking Scaling - 대상 추적 조정
      • 목표 지표를 설정하면 ASG가 해당 목표에 가까워지도록 인스턴스 수를 자동 조절
      • ex. 평균 CPU 사용률을 약 50%로 유지하거나, 대상 당 요청 수를 일정 수준으로 유지
      • 모든 조정 단계를 직접 정의하지 않아도 되어 편리함(ex. 70%를 넘으면 1대 추가, 90%를 넘으면 3대 추가 → 이처럼 하나하나 지정해주지 않아도 Auto Scaling이 CloudWatch 경보를 관리하고 필요한 조정을 수행함)
    2. Step Scaling - 단계별 조정
      • 지표가 임계값을 얼마나 초과했는지에 따라 서로 다른 규모로 조정
      • ex. CPU가 기준을 조금 초과하면 1대 추가, 훨씬 많이 초과하면 3대 추가
    3. Simple Scaling - 단순 조정
      • CloudWatch 경보가 발생하면 미리 지정한 하나의 조정 작업을 실행
      • ex. CPU가 임계값을 초과하면 2대 추가, 이후에는 쿨다운 기간동안 추가 조정 제한
      • Step Scaling보다 조정 규칙이 단순하며, AWS는 일반적으로 Target Tracking 또는 Step Scaling을 권장함
  • Scheduled Scaling - 예약 조정
    • 미리 정한 날짜와 시간에 ASG의 용량을 조정
    • ex. 매일 오전 8시 전에 인스턴스 수를 늘리고, 야간에는 줄임
    • 실시간 지표가 아니라 시간을 기준으로 동작
  • Predictive Scaling - 예측 조정
    • 과거의 부하 패턴을 분석해 앞으로 필요할 용량을 예측하고 미리 준비
    • ex. 평일 오전마다 트래픽이 급증하는 서비스에서 수요가 늘기 전에 인스턴스를 준비
    • 실제 부하가 높아진 뒤 반응하는 것만이 아니라, 예상되는 부하에 선제적으로 대응

Auto Scaling Types와 Scaling Policies는 서로 완전히 독립적인 개념이 아니라, Auto Scaling을 서로 다른 관점에서 분류한 것. 그래서 이름이 겹치는 항목은 이름만 같은 별개의 요소가 아니라 서로 같은 요소임

Auto Scaling 함께 알아둘 개념

심화 내용(SAA-C03 범위)

  1. Minimum, Desired, Maximum Capacity
    • Min = 2, Desired = 3, Max = 8이라면 일반적으로 인스턴스 3대를 목표로 운영하며, 자동 확장 시 최대 8대까지 늘어날 수 있음
    • Min = 최소 용량
    • Desired = 목표 용량
    • Max = 최대 용량
  2. Cooldown과 Warmup의 차이
    • Cooldown = 단순 확장 정책에서 조정 직후 추가 조정을 제한하는 시간
    • Instance Warmup = 새 인스턴스가 준비되는 동안 지표 집계 및 확장 판단에 미치는 영향 조절
    • Grace Period = 초기화 중인 인스턴스가 헬스 체크 실패로 조기에 교체되지 않도록 하는 시간
  3. Lifecycle Hooks
    • 인스턴스가 시작되거나 종료되는 과정에서 사용자 정의 작업을 수행할 시간 제공
    • ex. 인스턴스 시작 시 애플리케이션 설치와 초기화를 완료한 뒤 서비스에 투입하거나, 종료 전에 로그를 저장하고 작업을 정리하도록 할 수 있음.
  4. Instance Refresh
    • Launch Template나 AMI를 업데이트한 뒤 ASG의 기존 인스턴스를 순차적으로 교체할 때 사용하는 기능.
    • 애플리케이션 버전이나 운영체제 이미지를 업데이트하면서 한꺼번에 모든 인스턴스를 교체하는 위험을 줄이는 데 유용

고가용성, 내결함성, 내구성

도메인 1 클라우드 개념

  • High Availability: 장애가 발생하더라도 서비스를 계속 이용할 수 있도록 설계하는 것
  • Fault Tolerance: 구성 요소에 장애가 발생해도 서비스 중단이나 기능 저하를 최소화하며 계속 동작하도록 설계하는 것. 엄밀한 의미에서는 장애가 발생해도 서비스가 중단되지 않는 수준을 의미함
  • Availability: 서비스나 데이터에 필요할 때 접근하고 사용할 수 있는 정도
  • Durability: 저장한 데이터가 손실되지 않고 보존될 가능성 또는 데이터 보존의 신뢰성
  • High Availability와 Fault Tolerance의 차이
    • High Availability: 장애를 견디고 빠르게 복구
      • 장애 가능성을 완전히 제거하기보다는, 장애가 발생해도 서비스를 이용할 수 있는 상태를 유지하거나 빠르게 복구하도록 설계하는 데 초점
      • Multi-AZ를 통해 고가용성을 높일 수 있음. 단, 장애 감지, 트래픽 전환, 인스턴스 교체 등의 과정에서 일시적인 중단이나 지연이 발생할 수 있음
    • Fault Tolerance: 장애가 발생해도 계속 동작
      • 구성 요소가 고장나더라도 서비스가 중단되지 않도록 하는데 초점
      • 요청을 처리하는 구성 요소 하나가 실패해도 다른 구성 요소가 즉시 처리를 이어받고, 사용자 입장에서 서비스 중단이 발생하지 않도록 설계
      • Multi-AZ를 구성했다고 Fault Tolerance가 보장되는 것은 아님. 장애 전환이 얼마나 빠른지, 데이터가 일관되게 유지되는지, 의존 서비스도 정상인지에 따라 결과가 달라짐
    • 판단 기준
      • High Availability: 장애 발생 후 자동 복구, 서비스 중단 최소화, 다른 AZ로 전환 강조
      • Fault Tolerance: 구성 요소 하나가 고장 나더라도 서비스가 중단되지 않아야 함 강조
    • RTO / RPO
      • RTO(Recovery Time Objective): 장애 발생 후 서비스를 복구하기까지 허용되는 목표 시간
      • RPO(Recovery Point Objective): 장애 발생 시 허용할 수 있는 데이터 손실의 시간 범위
    • Availability와 Durability의 차이
      • Availability: 데이터에 접근할 수 있는가?
        • 필요한 시점에 데이터나 서비스를 사용할 수 있는 정도
        • 만약 중요한 파일이 S3에 저장되어 있는데, S3에 장애가 발생해 해당 파일을 일시적으로 읽을 수 없다면, 파일 자체가 삭제되지 않았더라도 그 시점의 가용성은 낮아진 것
      • Durability: 데이터가 손실되지 않고 보존되는가?
        • 저장된 데이터가 손실되지 않고 보존되는 정도
        • 파일을 저장한 뒤 서비스에 일시적인 접근 장애가 발생했더라도 파일이 그대로 보존되어 있다면 내구성은 유지된 것

ELB(Elastic Load Balancer)와 로드 밸런서 종류

도메인 3 클라우드 기술 및 서비스

  • 들어오는 트래픽을 여러 대상에 분산하여 애플리케이션의 가용성, 확장성, 안정성을 높이는 AWS 서비스
  • 많은 수의 트래픽이 몰려올 때, ELB가 없다면 특정 서버에 요청이 집중될 수 있음
  • ELB를 통해 여러 서버로 요청을 분산할 수 있고 특정 서버가 비정상 상태인 경우 ELB는 해당 서버를 정상 대상으로 취급하지 않고 트래픽을 다른 정상 대상으로 보낼 수 있음
  • ELB와 함께 알아야 할 개념
    • Target Group: 트래픽을 전달할 대상과 상태 확인 설정을 관리
    • Health Check: 대상이 정상적으로 요청을 처리할 수 있는지 확인
    • EC2 Auto Scaling: 필요에 따라 EC2 인스턴스 수를 조정
    • Amazon CloudWatch: 지표와 경보를 통해 모니터링 및 자동화 지원
    • → ELB와 Auto Scaling은 상호 보완적. ELB가 트래픽을 분배하고, Auto Scaling이 서버 수를 조절하면 트래픽 증가에 대응하는 확장 가능한 구조 형성 가능

ALB, NLB, GWLB

  • ALB(Application Load Balancer / Layer 7 / 응용 계층)
    • HTTP 요청의 경로, 도메인, 헤더 등 애플리케이션 내용을 분석해 라우팅
  • NLB(Network Load Balancer / Layer 4 / 전송 계층)
    • TCP, UDP, TLS 등의 연결과 네트워크 정보를 바탕으로 트래픽 전달
  • GWLB(Gateway Load Balancer / Layer 3 / IP 패킷)
    • 네트워크 트래픽을 방화벽이나 침입 탐지/방지 장비 같은 가상 네트워크 어플라이언스로 전달하고 분산
  • 즉, ALB와 NLB는 주로 애플리케이션 트래픽을 대상 서버에 분배하고, GWLB는 네트워크 트래픽을 보안/네트워크 장비에 투명하게 전달하는 데 집중

ALB, NLB, GWLB (Detailed Ver.)

심화 내용(SAA-C03 범위)

Application Load Balancer(ALB)

  • 핵심 기능: 콘텐츠 기반 라우팅
  • ex. 사용자 → ALB, 하나의 도메인으로 접속
  • 요청 내용에 따른 라우팅 규칙:
    1. 이미지 서비스 - Target Group A
    2. 주문 서비스 - Target Group B
    3. API 서비스 - Target Group C
    4. 그 외 요청 - Default Action
  • ALB는 다음과 같은 조건 활용 가능
    • Path-based routing: URL 경로에 따라 분배 ex. /api/*, /images/*
    • Host-based routing: 도메인 이름에 따라 분배 ex. shop.example.com, api.example.com
    • HTTP 헤더/메서드/쿼리 문자열 기반 라우팅: 요청 헤더, HTTP 메서드, 쿼리 문자열 등의 조건을 활용
    • Source IP 기반 규칙: 요청 출발지 IP를 조건으로 사용 가능
    • Listener, Listener Rule, Target Group
      • Listener: 어떤 프로토콜과 포트로 요청을 받을지 정의
      • Listener Rule: 요청을 어디로 보낼지 결정하는 조건과 동작
      • Target Group: 요청을 전달할 대상과 상태 확인 설정 관리
    • 요청 흐름 요약
      • Client → Listener → Listener Rule → Target Group → 대상 서버
    • ALB 용례
      • 일반적인 웹사이트나 웹 API
      • HTTP 요청을 URL 경로에 따라 서로 다른 서비스로 전달
      • 여러 도메인을 하나의 로드 밸런서로 처리
      • 마이크로서비스 또는 컨테이너 기반 웹 애플리케이션
      • HTTP 수준의 라우팅 및 기능이 필요한 경우
    • ALB Key Words
      • path-based routing, host-based routing, HTTP header, HTTP/HTTPS, Layer 7

Network Load Balancer(NLB)

  • HTTP 요청의 URL 내용을 분석하는 대신 네트워크 연결과 프로토콜 정보를 바탕으로 트래픽을 분산
  • 핵심 특징
    1. 높은 처리량과 낮은 지연 시간: 대량의 연결과 높은 성능이 필요한 워크로드에 적합 ex. 게임 서버, 실시간 통신, TCP 기반 서비스
    2. 가용 영역별 고정 IP 주소: NLB는 가용 영역별로 고정 IP를 제공할 수 있으며, 필요하면 각 가용 영역에 Elastic IP를 연결할 수도 있음
    3. 클라이언트 원본 IP 보존: 구성에 따라 클라이언트의 원본 IP를 백엔드 대상에서 확인할 수 있도록 지원
    4. TCP, UDP, TLS 처리
      • TCP 기반의 자체 프로토콜 서버
      • UDP 기반 서비스
      • TLS 연결을 NLB에서 종료하는 구성
      • TCP Listener를 통해 TLS 트래픽을 암호화 상태로 전달하는 구성
    • NLB Key Words
      • Static IP, TCP/UDP, Low latency

Gateway Load Balancer(GWLB)

  • 단순히 웹 서버나 애플리케이션 서버에 요청을 분산하는 것이 아니라, 방화벽이나 침입 탐지/방지 시스템 같은 가상 장비를 트래픽 경로에 배치하고 확장하는 데 사용
  • GWLB가 필요한 이유
    • 일반적인 구조에서 방화벽을 여러 대 운영해야 대량의 트래픽 처리가 원활함. 그러나 방화벽을 여러 대 운영할 경우 어떤 트래픽을 어느 장비로 보낼지, 동일한 통신 흐름이 같은 장비를 거치도록 어떻게 관리할지 등의 문제가 생김 → 이런 문제를 해결해주는게 바로 GWLB
    • 여러 가상 어플라이언스에 트래픽을 분산하며, 동일한 흐름의 패킷을 일관되게 같은 대상으로 전달함

ALB와 NLB의 배치

  • ALB 배치 방식(트래픽 분산 기준, 네트워크상에서의 위치)
    • Layer 7에서 동작, HTTP/HTTPS 요청을 분석해 적절한 Target Group으로 전달
    • 요청의 내용을 읽고 판단할 수 있기 때문에 웹 애플리케이션이나 마이크로서비스를 운영할 때 유용
  • NLB 배치 방식(트래픽 분산 기준, 네트워크상에서의 위치)
    • Layer 4에서 동작, 주로 TCP, UDP, TLS 연결을 기준으로 트래픽 전달
    • ALB처럼 URL 경로나 HTTP 헤더를 해석해 라우팅하지는 않음
    • 주요 특징
      • 매우 높은 처리량과 낮은 지연시간이 필요한 서비스에 적합
      • 고정 IP(Elastic IP)가 필요한 아키텍처에 적합, 필요에 따라 각 가용 영역에 Elastic IP 연결 가능
      • HTTP가 아닌 TCP/UDP 기반 애플리케이션에도 사용 가능
      • 클라이언트의 원본 IP 주소를 백엔드에 보존할 수 있는 구성이 있음
  • ALB는 HTTP 요청을 이해하고, NLB는 네트워크 연결을 전달함

X-Forwarded-For(XFF) 헤더

심화 내용(SAA-C03 범위)

  • HTTP 요청이 어떤 클라이언트에서 시작되었는지 확인할 수 있도록 클라이언트의 IP 주소를 전달하는 헤더
  • 왜 XFF 헤더가 필요할까?
    • 클라이언트가 ALB를 통해 EC2에 접속하면, EC2가 보는 네트워크 연결의 상대방은 일반적으로 원래 클라이언트가 아니라 로드 밸런서임
    • 따라서 웹 서버가 단순히 연결의 원본 IP만 기록하면 클라이언트의 IP를 확인하기 어려울 수 있음. ALB는 기본 설정에서 XFF 헤더에 클라이언트 IP를 추가해 백엔드로 전달함
    • XFF 헤더를 통해 애플리케이션은
      • 웹 서버 로그에 클라이언트 IP 기록
      • 접속 통계 및 요청 분석
      • IP 기반 접근 제어 등을 할 수 있음
    • 단, XFF 헤더에 적힌 IP를 무조건적으로 신뢰하면 안 됨
    • 클라이언트가 조작한 XFF 값을 보낼 수 있기에 프록시 경로와 헤더 처리 방식을 고려해 판단해야 함
    • NLB는 지원되는 대상 유형 및 설정에 대해 네트워크 연결의 원본 IP를 직접 보존함
    • NLB와 Proxy Protocol v2를 함께 사용하는 경우 특정 구성에서 원본 IP 등 연결 정보를 별도의 프로토콜 헤더로 전달함
    • 즉, NLB는 L4에서 동작하므로 적절한 구성에서는 IP 패킷의 원본 주소 자체를 보존할 수 있지만, 특정 구성에서는 원본 IP가 그대로 보존되지 않을 수 있음. 이때 Proxy Protocol v2를 사용하면 원본 연결 정보를 전달할 수 있음
    • 함께 알아두면 좋은 X-Forwarded 헤더
      1. X-Forwarded-Proto: 클라이언트가 ALB에 연결할 때 사용한 프로토콜 ex. https
      2. X-Forwarded-Port: 클라이언트가 ALB에 연결할 때 사용한 포트 ex. 443

Cross-Zone Load Balancing

심화 내용(SAA-C03 범위)

  • 로드 밸런서가 특정 AZ에 들어온 트래픽을 다른 AZ에 있는 대상 인스턴스에도 분산할 수 있도록 하는 기능
  • AZ별로 인스턴스 수가 다르더라도 전체 인스턴스에 트래픽을 고르게 분산할 수 있는 특징을 지님
  • Cross-Zone Load Balancing은 인스턴스의 수를 조정하는 것이 아니라, 기존 인스턴스들을 AZ 경계와 상관없이 활용할 수 있도록 해주는 기능
  1. Cross-Zone Load Balancing이 없는 경우
    • AZ - A와 AZ - B 존재, AZ - A에는 2개의 인스턴스, AZ - B에는 1개의 인스턴스 존재
    • AZ - A와 AZ - B로 트래픽이 절반씩 들어온다고 가정 시 AZ - A에 존재하는 인스턴스는 각각 25%의 트래픽을 받지만, AZ - B에 존재하는 1개의 인스턴스는 50%의 트래픽을 받음
    • → 결과적으로 AZ - B에 있는 인스턴스가 다른 인스턴스보다 상대적으로 많은 부하를 받게 됨
  2. Cross-Zone Load Balancing이 활성화된 경우
    • 각 AZ의 로드 밸런서 노드가 다른 AZ에 있는 대상 인스턴스에도 트래픽을 전달할 수 있음
    • 즉, 아까와 같은 상황에서 AZ - B에 몰렸던 트래픽을 AZ - A에 존재하는 인스턴스로 전달하여 특정 AZ의 인스턴스에 부하가 집중되는 현상을 줄일 수 있음
Cross-Zone Load Balancing의 활성화 여부
로드 밸런서기본값설명
ALB활성화기본으로 AZ 간 트래픽 분산 수행
NLB비활성화수동으로 활성화하면 AZ 간 트래픽 분산이 가능하지만, 교차 AZ 데이터 전송 비용이 발생할 수 있음

Session State와 Sticky Session

심화 내용(SAA-C03 범위)

Sticky Sessions(세션 고정)

  • 같은 사용자의 요청을 일정 기간 같은 대상으로 전달하도록 하는 기능
  • ex. EC2 A의 메모리에 세션이 저장되어 있다면, 해당 사용자의 후속 요청도 A로 전달되도록 설정할 수 있음
    • 단, 단점도 존재
      1. A가 장애를 일으키면 세션 정보가 유실될 수 있음
      2. 트래픽이 특정 인스턴스에 몰릴 수 있음
      3. Auto Scaling으로 인스턴스가 추가되어도 부하가 항상 균등하게 분배되지는 않음
    • → Sticky Session이 항상 나쁜 것은 아니지만, 가능하다면 세션을 외부에서 공유해 서버 간 의존성을 줄이는 설계(External Session Storage)가 확장성과 장애 대응 측면에서 유리한 경우가 많음
  • Session State: 사용자가 웹 서비스와 상호작용하는 동안 유지해야 하는 사용자별 정보 → 기억해야 할 정보
  • Session Stickiness: 동일한 사용자의 요청을 동일한 서버로 계속 전달하는 기능 → 같은 서버에 계속 연결하는 방법

Session State란?

  • ex. 온라인 쇼핑몰
  • 사용자가 다음과 같은 행동을 했다고 가정
    1. 쇼핑몰에 로그인
    2. 상품 A를 장바구니에 담음
    3. 상품 B를 장바구니에 담음
    4. 결제 페이지로 이동
  • 이 과정에서 서버는 사용자의 로그인 정보와 장바구니 정보를 유지해야 함
  • 이러한 사용자별 정보를 Session State라고 함

Session State와 Load Balancing의 관계

  • ex. Session State가 서버 내부에 저장된 케이스
  • 두 대의 EC2 인스턴스가 ALB 뒤에서 작동한다고 가정
  • 사용자의 첫 번째 요청이 EC2 1로 전달되면 EC2 1은 로그인 정보와 장바구니 정보를 저장
  • 그런데 다음 요청이 Load Balancing에 의해 EC2 2로 전달되면 EC2 2에는 사용자의 세션 정보가 없기 때문에 문제가 발생할 수 있음
  • → 이 문제를 해결할 수 있는 방법 중 하나가 바로 Sticky Session임

Session Stickiness란?

  • Session Stickiness(세션 고정)는 특정 사용자의 요청을 동일한 서버로 지속적으로 전달하는 기능
  • AWS ALB에서는 이를 Sticky Session 또는 Session Affinity라고 부름
  • ALB의 Sticky Session은 쿠키를 기반으로 작동
    • 작동 과정
      1. 최초 요청 - 브라우저가 ALB에 HTTP 요청을 보냄. 이때는 쿠키가 없는 상태
      2. ALB가 인스턴스 선택 - ALB가 EC2 1을 선택하여 요청 전달
      3. ALB가 쿠키 발급 - EC2 1의 응답을 브라우저에 전달하면서 ALB가 생성한 쿠키를 응답에 포함
      4. 브라우저가 쿠키 저장 - 브라우저는 응답에 포함된 쿠키를 저장
      5. 이후 요청에 쿠키 포함 - 브라우저가 다음 요청을 보낼 때 저장된 쿠키를 함께 전송
      6. ALB가 기존 인스턴스로 전달 - ALB는 쿠키를 확인하여 이전에 선택했던 EC2 1로 요청 전달
    • 즉, ALB가 사용자를 식별하는 데 쿠키를 활용하여 동일한 서버로 요청을 전달하는 것

ALB의 Sticky Session 유형

  • Duration-based: ALB가 생성한 쿠키의 유효기간을 설정
  • Application-based: 애플리케이션이 생성한 쿠키를 기반으로 세션 고정
  • 시험에서는 ALB Sticky Session - Cookie 기반으로 동일한 대상에 요청을 전달한다는 기능에 집중하면 됨

Sticky Session의 한계

  • Sticky Session으로 Session State 문제가 완전히 해결되는 것은 아님
  • 만약 사용자 A의 정보가 EC2 1에 모두 저장되어 있었는데, EC2 1에 장애가 발생한다면?
  • 사용자 A는 다른 인스턴스로 연결될 수 있지만, 기존 세션 정보가 타 인스턴스로 자동으로 이전되는 것은 아님
  • 따라서 Sticky Session은 세션 정보를 복제하거나 공유할 수 없고, 단순히 동일한 서버로 요청을 전달하는 기능

External Session Storage(외부 세션 저장소)

  • Sticky Session이 가지는 한계를 해결하기 위해 사용하는 방법
  • Sticky Session보다 더 권장되는 아키텍처
  • 세션 정보를 개별 EC2 인스턴스 내부에 저장하는 대신, 여러 인스턴스가 접근할 수 있는 별도의 저장소에 보관하는 방법(AWS의 경우 Amazon ElastiCache를 활용하여 구현 가능)
  • ex.
    1. 사용자 A의 요청이 EC2 1에 전달
    2. EC2 1은 로그인 정보와 장바구니 정보를 ElastiCache에 저장
    3. 다음 요청이 EC2 2에 전달되더라도 ElastiCache에서 동일한 세션 정보를 조회
    4. 따라서 사용자는 서버가 바뀌어도 로그인 상태와 장바구니 정보 유지 가능
  • 단, External Session Storage를 활용한다고 해서 모든 장애 문제가 해결되는 것은 아님
  • External Session Storage를 구현하기 위해 ElastiCache를 사용하기에 ElastiCache가 중요한 구성 요소이므로, ElastiCache 자체의 가용성도 확보해야 함
    1. Primary와 Replica 구성(Automatic Failover - 자동 장애 조치)
      • 복제와 자동 장애 조치는 Valkey/Redis OSS 엔진 기준이며, Memcached는 복제와 자동 장애 조치를 지원하지 않음
      • 작동 과정
        1. AZ-A의 Primary가 세션 데이터 저장
        2. 해당 데이터가 AZ-B의 Replica로 복제
        3. AZ-A의 Primary에 장애 발생
        4. AWS가 Replica를 새로운 Primary로 승격
        5. 애플리케이션은 새로운 Primary를 통해 세션 데이터를 조회하고 저장
        • 단, 복제는 일반적으로 비동기 복제(Async)이므로 장애 직전의 일부 데이터가 복제되지 못할 가능성이 있음. 또한 장애 조치 중에는 일시적인 연결 중단이 발생할 수 있음

ALB, Auto Scaling, External Session Storage(by ElastiCache) 전체 아키텍처

  • 전체 요청 흐름
    1. 사용자가 ALB에 요청
    2. ALB가 여러 EC2 인스턴스 중 하나로 요청을 전달
    3. EC2는 ElastiCache에서 사용자의 세션 정보를 조회
    4. 세션 정보가 존재하면 로그인 상태와 사용자 정보 확인
    5. 사용자의 요청을 처리하고 필요한 세션 정보를 갱신
    6. ElastiCache의 Primary 데이터는 다른 AZ의 Replica에도 복제

SSL/TLS Termination과 End-to-End Encryption

심화 내용(SAA-C03 범위)

SSL/TLS Termination(SSL/TLS 종료)

  • HTTPS 통신
    • HTTP 통신에 TLS 암호화를 적용한 것
    • 일반적으로 클라이언트와 서버 사이에서 TLS 연결을 설정하고 데이터를 암호화하여 주고 받음
  • AWS에서 ALB를 사용하는 경우, EC2(서버)가 직접 TLS 암호화를 처리하지 않고 ALB가 대신 처리하도록 구성할 수 있는데 SSL/TLS Termination이 그것임
  • SSL/TLS Termination 작동 과정
    • SSL/TLS Termination 구조
      • 브라우저 → ALB → 서버(EC2 인스턴스)
      • ALB(TLS Termination)
        1. SSL/TLS 인증서로 클라이언트와 TLS 연결
        2. 암호화된 HTTPS 요청 복호화
        3. HTTP 요청으로 전달할 수 있도록 처리
    • 단계별 순서
      1. 사용자(Client)가 브라우저에서 HTTPS 요청을 보냄
      2. ALB의 HTTPS Listener가 요청을 받음
      3. ALB는 등록된 SSL/TLS 인증서를 사용하여 TLS 연결을 설정
      4. ALB가 암호화된 요청 복호화
      5. ALB가 HTTP 요청을 EC2 instance로 전달
      6. EC2는 복호화 작업 없이 애플리케이션 처리에만 집중
      • SSL/TLS 인증서는 AWS Certificate Manager를 통해 발급하거나 가져올 수 있음
      • ALB에 HTTPS Listener를 생성하려면 서버 인증서와 TLS 보안 정책이 필요
  • SSL/TLS Termination을 사용하는 이유
    1. EC2의 처리 부담 감소
      • TLS 암호화와 복호화에는 CPU 자원이 사용됨
      • ALB가 이 작업을 대신하면 EC2는 애플리케이션 로직 처리에 더 집중 가능
    2. 인증서 관리의 편리성
      • EC2가 여러 대라면 각각의 EC2에 인증서를 설치하고 관리해야 할 수 있음
      • 하지만 ALB에서 TLS Termination을 수행하면 인증서를 ALB에 집중하여 관리할 수 있음
    3. 확장성 및 관리 편의성
      • Auto Scaling으로 EC2가 추가되거나 교체되더라도 개별 인스턴스에 HTTPS 인증서를 설치할 필요가 없는 구조를 만들 수 있음

SSL/TLS Termination과 End-to-End Encryption 비교

  1. SSL/TLS Termination
    • 클라이언트 → ALB만 암호화(HTTPS 연결)
    • ALB와 EC2 간의 연결은 암호화되어있지 않음(HTTP 연결)
    • ALB에서 복호화한 후 EC2에 HTTP로 전달하는 구조
  2. End-to-End Encryption
    • ELB에서만 사용되는 특정 기능의 명칭이 아니라 통신의 양 끝단 사이에서 암호화가 유지되는 구조를 설명하는 개념
    • ALB Case(TLS 재암호화)
      • 클라이언트 → ALB → EC2 모두 암호화(모두 HTTPS 연결)
      • 클라이언트에서 ALB로 넘어올 때, TLS 복호화 후 다시 암호화하여 EC2에 전달
      • 이 경우 ALB의 Target Group 프로토콜을 HTTPS로 설정하고, EC2에서도 HTTPS 통신을 처리하도록 구성해야 함
      • ALB에서 TLS 연결이 한 번 종료되고, EC2와 새로운 TLS 연결을 맺는 구조
      • 클라이언트와 EC2 사이에 하나의 TLS 연결이 그대로 유지되는 것은 아님
    • NLB Case(TLS Pass-through)
      • 클라이언트 → NLB(TCP Listener) → EC2 모두 암호화
      • 클라이언트로부터 받은 TLS 연결을 복호화/종료하지 않고 동일한 TLS 연결의 암호화 데이터를 EC2에 전달
      • EC2는 전달받은 TLS 연결을 TLS 복호화 및 처리
    • End-to-End Encryption은 로드 밸런서와 EC2 간의 연결의 보안을 강화하지만, SSL/TLS Termination의 장점이던 EC2의 처리 부담 감소 효과까지 기대할 수는 없음
    • 두 구조는 보안성과 성능 사이의 설계 선택으로 특정 구조가 더 낫다고 단정할 수 없음

  • 여러 AWS 계정의 비용을 하나의 계정에서 통합 관리하고 비용 절감 혜택을 활용하려면 Consolidated Billing을 사용합니다.

SCP(Service Control Policies) 기초

도메인 2 보안 및 규정 준수

SCP는 조직 Root, OU 또는 개별 계정에 적용하여 AWS 서비스 및 작업에 대한 최대 권한 범위(Maximum Permissions)를 정의하는 정책입니다.

  • 특정 AWS 서비스나 작업을 사용하지 못하도록 제한할 수 있습니다.
  • 조직 전체 또는 특정 OU, 계정에 적용할 수 있습니다.
  • Member Account의 IAM 사용자, 역할, 루트 사용자는 SCP가 허용한 범위를 넘는 권한을 사용할 수 없습니다.
  • SCP 자체는 권한을 부여하지 않습니다.
  • 예: 회사의 모든 계정에서 특정 리전 이외의 AWS 리전을 사용하지 못하도록 제한

시험 포인트

  • 특정 OU에 속한 계정들의 서비스 사용 제한 → SCP
  • 계정의 최대 권한 범위 제한 → SCP
  • SCP는 계정에 부여할 수 있는 최대 권한을 제한하며, 직접 권한을 부여하지 않습니다.
  • 기본 설정에서는 모든 작업을 허용하는 SCP(FullAWSAccess)가 연결되어 있어, 보통은 막을 작업만 Deny하는 방식으로 씁니다. 허용한 작업만 쓰게 하는 방식(Allow List)에서는 허용하지 않은 작업이 막힙니다.
  • 정책은 상위에서 하위로 상속되고, 명시적 Deny가 항상 우선합니다.
  • SCP는 Management Account 자체에는 적용되지 않습니다.

AWS Organizations 구조

심화 내용(SAA-C03 범위)

여러 AWS 계정을 하나의 조직으로 묶어 중앙에서 관리하고, 계정별 권한과 정책을 통제하는 서비스입니다. 개발, 운영, 보안, 테스트 환경을 한 계정에 섞어 두면 권한과 리소스가 뒤섞이므로, 계정을 목적별로 나누고 그룹화해 관리합니다.

계층 구조

  • Management Account: 조직을 만들고 중앙에서 관리하는 계정
  • Root(조직 Root): 조직의 최상위 컨테이너입니다. K8s나 Docker의 컨테이너가 아니라, 모든 OU와 계정을 담는 논리적 최상위 공간입니다.
  • OU(Organizational Unit): 목적에 따라 계정을 묶는 단위입니다. OU 안에 다른 OU를 만들 수 있습니다(예: Root → Business OU → Development OU → Account A).
  • Account: 실제 리소스를 만들고 운영하는 계정
  • 상위 OU에 설정한 정책은 하위 OU와 계정에 적용됩니다.

용어 주의: Root와 Root User

  • 조직 Root는 조직의 최상위 컨테이너이고, Root User는 각 계정의 최고 권한 사용자(이메일로 로그인)입니다. 서로 다른 개념입니다.
  • Management Account도 Root 컨테이너에 포함되지만 SCP는 적용되지 않습니다.
Management Account와 Member Account
구분역할
Management Account계정 생성, 기존 계정 초대, OU 생성과 계정 이동, 조직 전체에 정책 연결, 통합 결제(Consolidated Billing) 관리
Member AccountEC2, S3, RDS 등 실제 워크로드 운영. Organizations 정책(SCP)의 통제를 받음
  • SCP가 Management Account에는 적용되지 않으므로, AWS는 Management Account에 실제 워크로드를 두지 않는 것을 권장합니다.

Organizations API

심화 내용(SAA-C03 범위)

콘솔에서 클릭해서 하던 계정과 조직 구조 관리 작업을 CLI/SDK/API로 자동화하는 인터페이스입니다.

  • CreateOrganization: 새 조직 생성
  • CreateAccount: 새 AWS 계정 생성
  • InviteAccountToOrganization: 기존 계정을 조직에 초대
  • CreateOrganizationalUnit: OU 생성
  • MoveAccount: 계정을 다른 OU로 이동
  • CreatePolicy: 새 조직 정책 생성
  • AttachPolicy: 정책을 Root, OU, 계정에 연결
  • RegisterDelegatedAdministrator: 멤버 계정을 위임 관리자로 등록

예: 새 개발팀이 생기면 CreateAccount → CreateOrganizationalUnit → MoveAccount → AttachPolicy 순으로 자동화할 수 있습니다.

주의

  • 이 API는 계정 생성, 초대, 이동, 정책 연결을 자동화할 뿐, EC2나 S3 같은 서비스 자체를 만드는 기능이 아닙니다.

SCP(Service Control Policy)와 상속

심화 내용(SAA-C03 범위)

SCP란?

  • 조직 안 계정의 IAM User와 IAM Role이 사용할 수 있는 최대 권한의 범위를 제한하는 정책입니다.
  • SCP는 권한을 부여하지 않고 제한합니다. 실제로 쓸 수 있는 권한은 IAM 정책 등 권한 부여 정책과 SCP가 허용하는 범위의 교집합입니다.
  • 예: IAM Policy가 S3를 Allow해도 SCP가 S3를 Deny하면 접근 불가입니다. 반대로 SCP가 막지 않아도 IAM Policy가 권한을 주지 않았다면 접근 불가입니다.

적용 대상과 예외

  • 연결 위치: 조직 Root, OU, Member Account
  • 영향받는 대상: Member Account의 IAM User, IAM Role, Root User
  • Management Account에는 적용되지 않고, 서비스 연결 역할(Service-linked role)도 SCP의 제한을 받지 않습니다.

전략: Deny List와 Allow List

Deny List

  • 기본적으로 모두 허용하고 특정 서비스나 작업만 명시적으로 거부(예: CloudTrail 비활성화 금지)
  • 새 서비스가 추가돼도 허용 정책을 추가할 필요가 적고 관리가 간단함

Allow List

  • 명시적으로 허용한 서비스와 작업만 사용 가능(예: EC2, S3, RDS만 허용)
  • 엄격한 통제로 규제가 심한 환경에 적합하지만, 새 서비스를 쓰려면 SCP를 수정해야 하고 관리가 복잡함

AWS는 기본으로 모든 서비스를 허용하는 관리형 SCP인 FullAWSAccess를 Root, OU, 계정에 연결해 둡니다. 그래서 기본 설정에서는 Deny List가 쉽고, Allow List를 쓰려면 FullAWSAccess를 제거하고 필요한 권한만 허용하는 SCP로 대체해야 합니다.

상속 원칙

  1. 상위 OU의 SCP는 하위 OU와 계정에 적용됩니다.
  2. Allow는 대상 계정까지 이어지는 모든 계층에서 허용되어야 합니다(계층별 허용 범위의 교집합).
  3. Deny는 경로상 어느 한 계층에서라도 걸리면 하위 계정의 해당 작업을 차단합니다. 명시적 Deny가 항상 우선합니다.
Allow List 상속 예시
계층SCP가 허용하는 서비스
RootEC2, S3, RDS
Development OUEC2, S3
Account AEC2, S3, RDS
결과(교집합)EC2, S3 (RDS는 중간 OU에서 허용되지 않아 사용 불가)

Deny 예: Root와 Account A에서 EC2가 Allow여도, 중간의 Development OU에서 Deny이면 Account A는 EC2를 쓸 수 없습니다.

IAM Policy vs Permissions Boundary vs SCP

심화 내용(SAA-C03 범위)

구분역할비유
IAM Policy실제로 어떤 작업을 할 수 있는지 권한을 부여직원에게 실제 업무 권한 부여
Permissions Boundary특정 IAM User/Role이 가질 수 있는 최대 권한 제한직원 권한의 상한선
SCPOrganizations 소속 계정 전체의 최대 권한을 조직 차원에서 제한회사 전체의 업무 범위 제한
  • IAM Policy에 Allow가 있어도 Permissions Boundary, SCP, 명시적 Deny 등을 함께 평가하므로 접근이 보장되지는 않습니다.
  • Organizations 환경의 유효 권한은 IAM Policy ∩ Permissions Boundary ∩ SCP입니다(명시적 Deny는 항상 우선).
  • 대상이 다릅니다. Permissions Boundary는 특정 IAM User/Role, SCP는 Member Account의 IAM User, Role, Root User입니다.
  • 예: 모든 계정에서 특정 리전 밖의 사용을 금지하려면 계정마다 정책을 만들 필요 없이 Root나 OU에 SCP 하나를 연결합니다.

Permissions Boundary 위임 시나리오

  • 개발팀 관리자에게 IAM User 생성 권한을 위임하되, 지정된 Permissions Boundary를 붙여야만 생성되도록 조건(iam:PermissionsBoundary 조건 키)을 겁니다.
  • 그러면 관리자가 어떤 정책을 붙여도 경계를 넘는 권한은 쓸 수 없어 권한 상승을 막습니다.
  • 시험 키워드: Delegate IAM permission management safely / Prevent privilege escalation / Set the maximum permission for IAM users or roles

AWS Control Tower와 Landing Zone

심화 내용(SAA-C03 범위)

Organizations가 다중 계정 관리의 기본 틀이라면, Control Tower는 그 위에 보안과 운영 환경을 자동으로 구축하고 관리하는 서비스입니다. Organizations를 대체하지 않고, 이를 기반으로 더 높은 수준의 자동화와 거버넌스를 제공합니다.

Landing Zone

조직이 AWS를 안전하고 일관되게 쓰도록 미리 구성해 둔 다중 계정 기반 환경입니다. 계정 구조뿐 아니라 보안, 접근 권한, 로그 수집, 감사 체계까지 포함합니다.

  • AWS Organizations: 계정과 OU의 계층 관리
  • AWS IAM Identity Center: 사용자와 그룹의 중앙 집중식 접근 관리
  • AWS CloudTrail: API 활동 기록
  • AWS Config: 리소스 구성과 변경 추적
  • Control Tower Controls: 보안과 운영 규칙 적용
  • Account Factory: 표준화된 신규 계정 생성
  • 설정 이탈(Drift) 감지도 제공합니다.

Shared Accounts: 핵심 계정 3가지

Management Account
Control Tower를 설정하고 조직 전체를 관리합니다(Organizations, 계정과 OU, Account Factory, Controls, 통합 결제). 관리 권한이 집중된 계정이므로 일반 서비스나 프로덕션 워크로드를 두지 않고 별도 Member Account를 씁니다.
Log Archive Account
여러 계정의 CloudTrail과 AWS Config 로그를 중앙에서 수집하고 보관합니다. 목적은 로그의 중앙 보관과 감사 증거 확보이며, 로그를 모으는 계정과 워크로드 계정을 분리합니다. 예: 누가 언제 S3 버킷 정책을 바꾸거나 EC2를 삭제했는지 CloudTrail로 조사합니다.
Audit Account
조직 전체의 보안 상태와 규정 준수 여부를 점검하는 계정입니다. 로그를 저장하는 Log Archive와 구분하세요. 보안팀이 S3 공개 여부나 EBS 암호화 여부를 확인할 때, Cross-account role로 다른 계정의 리소스에 접근할 수 있게 합니다.

Controls(Guardrails)

심화 내용(SAA-C03 범위)

계정들이 보안과 운영 규칙을 지키도록 통제하는 기능입니다. 예전 명칭은 Guardrails이고, 최신 공식 문서는 Controls라고 부릅니다. SCP와 같은 개념이 아니라, SCP는 Organizations의 정책 기능이고 Controls는 Control Tower가 제공하는 더 포괄적인 통제 체계입니다.

Controls의 3가지 유형
유형동작주요 구현 방식
Preventive(예방적)위반 작업을 사전에 차단(예: 금지된 리전에서 EC2 생성 거부)SCP, RCP, Declarative Policies
Detective(탐지적)이미 만들어진 리소스가 정책을 위반하는지 탐지하고 보고(차단이나 자동 수정은 아님)AWS Config Rules
Proactive(선제적)리소스 생성 전에 규칙 준수 여부를 검사(예: 위반 CloudFormation 템플릿 배포 차단)CloudFormation Hooks
  • 시험에서는 Preventive Control을 SCP로 떠올리면 좋습니다(단, 모든 예방적 통제가 SCP만으로 구현되지는 않음).
  • Proactive Control은 CloudFormation으로 배포되는 리소스만 검사합니다. 수동 작업이나 다른 배포 도구는 자동으로 검사하지 않습니다.

Control의 중요도(위 유형과 별개의 분류)

  • Mandatory: 필수 통제. Landing Zone 설정 시 자동으로 적용되며 비활성화할 수 없음
  • Strongly Recommended: AWS가 강하게 권장하는 통제
  • Elective: 조직의 필요에 따라 선택하는 통제

Account Factory

심화 내용(SAA-C03 범위)

미리 정의된 표준 설정에 따라 새 AWS 계정을 만드는 기능입니다. 수동으로 하면 계정 생성, 조직 등록, 보안 정책, 접근 권한, 로그 수집, 네트워크 구성을 매번 해야 하는데, Account Factory는 표준 템플릿으로 한 번에 프로비저닝하고 새 계정을 조직의 거버넌스 체계에 편입시킵니다.

기초 용어

특권 명령과 Bare-Metal

  • 특권 명령은 시스템 요소들과 소통할 수 있는 명령으로, OS만 쓸 수 있습니다.
  • OS는 특권 명령 때문에 하드웨어 시스템 하나당 하나만 돌아갈 수 있습니다. 일반 프로그램은 특권 명령이 필요 없어서 많은 프로그램을 동시에 실행할 수 있습니다.
  • 가상화가 나타나기 전에는 하드웨어 시스템 하나가 OS 하나만 실행할 수 있었습니다. 일반 컴퓨터처럼 OS를 하드웨어에 직접 설치한 상태(Bare-Metal)로만 운영했습니다.
